# 全局规则

代码清楚好读，结构简单，及时清理无用实现。减少无效操作和重复验证，使用 Git 保存修改记录。

## 沟通与执行

1. 默认使用自然、直接的中文，结论先行，保留影响判断的条件、依据和未验证事项。
2. 不写防御性说明，不回应用户没有提出的反驳，不堆免责声明和重复解释。
3. 只澄清影响结果的关键歧义，其余采用合理默认值继续完成。
4. 已授权的工作持续推进到完成。最终简要说明结果、必要验证和未完成事项，不复述操作过程。
5. 区分事实、推断和假设，未执行的检查不得声称通过。

## 必备技能

1. 环境初始化时安装 `karpathy-guidelines` 和 `humanizer`，使用指定来源和明确版本。已安装时复用，主动升级时再更新。
2. 写代码、审查和重构使用 `karpathy-guidelines`；润色文章和文档使用 `humanizer`。
3. 技能缺失时如实说明，遵循其核心原则继续可完成的工作。用户明确要求和项目约束优先于技能中的一般建议。

## 代码与结构

1. 使用满足当前需求的最简单实现，命名清楚、流程直接，避免复杂嵌套和炫技写法。
2. 不添加未要求的功能，不为假想需求增加配置、兼容层、抽象或框架。优先复用现有代码、标准库和已有依赖。
3. 按功能组织代码，相关实现集中放置，函数和模块职责清楚。已有项目沿用合理结构，新项目从最少的文件和层级开始。
4. 文件承担多个独立职责、影响理解时再拆分，不机械规定行数，不预建空目录。
5. 注释解释原因和必要限制，不复述代码。修改围绕当前任务展开，不顺手重构无关模块。

## 错误处理与代码清理

1. 只处理真实可能发生且需要处理的失败，不为想象中的风险堆叠判断、重试和兜底。
2. 外部输入与实际失败边界按需校验，内部已保证的条件不逐层重复检查。
3. 异常只有在能有效处理时才捕获。错误清楚暴露，不用空结果、默认值或静默跳过掩盖问题。
4. 修复根因，替换旧实现时同步清理失效分支，避免补丁不断叠加。
5. 在处理到的模块中，确认无用的代码、依赖、配置和注释掉的旧实现直接删除，包括历史遗留内容。判断用途时考虑对外入口和动态加载，不只看静态引用。
6. 清理范围跟随当前任务，不额外发起全仓库扫描。

## 验证与 token 使用

1. 修改前明确完成条件，选择能证明本次改动有效的最少必要检查，遵守项目明确要求。
2. 优先复用已有测试和已确认的信息。按需读取文件，合并独立查询，避免重复搜索、重复读取和大段日志。
3. 局部改动优先验证相关行为，不为简单改动编写没有实际价值的测试或报告。
4. 必要检查通过后立即结束。只有后续修改影响结果、检查失败、已知不稳定或出现具体新问题时才重跑。
5. 不为“再保险”反复构建、测试、截图或审查。

## Git

1. 代码项目默认使用 Git。确认项目根目录后，为尚未纳入仓库的项目初始化 Git；已有仓库直接沿用。
2. 修改前查看状态，保留用户已有改动。
3. 每完成一项独立改动并通过必要验证后创建本地提交，只包含本次任务相关内容，提交信息说明实际变化。
4. 缓存、构建产物和临时文件通过 `.gitignore` 管理，旧代码通过 Git 历史追溯。
5. 按用户要求推送远程；重写历史或丢弃已有改动前取得明确授权。

## 项目文件

1. 每个项目根目录维护 `AGENTS.md` 和 `YAN.md`。
2. 项目 `AGENTS.md` 只记录重要且长期有效的代码入口、运行环境、必要检查和项目约束，不记录操作流水账和任务完成情况。
3. `YAN.md` 保持非常精简，保留项目介绍、已完成、正在进行、已发现的问题和下一步，只记录实质项目进展、重要研究工作、关键实验结果及影响实验的问题。Git 连接、提交同步、常规文件整理等琐事不列入。所有大标题下统一用 `1.`、`2.`、`3.`……列小点，每部分重新编号；实验记录一个实验占一个编号，内容只写一句话，随后用“具体”和“实验结果”引用对应 Markdown 文件，尚无文件时标明待补充或待产出。
4. 开始或接手任务时读取项目规则和进度，已读取且未变化时复用；重要规则、进展或问题变化时再更新。
